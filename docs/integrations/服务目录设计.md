# 日志服务目录与代码仓库映射设计

## 1. 目标与归属

`log-search` 已是日志查询平台、namespace、env、app 配置的事实源。服务与 GitLab 仓库的对应关系也应由 `log-search` 管理：每次新增日志接入时，在同一处登记服务元数据；查询 Agent 通过 log-search MCP 动态读取映射。

Codex Skill 只描述通用排查流程，不保存具体平台、服务、仓库或分支数据。因此，新增服务或调整仓库映射只需更新 log-search 服务目录，不必重新安装/更新 Skill。

GitLab MCP 负责项目、分支、源码和 MR 的实际读取/写入；它不作为服务归属的事实源。服务目录保存 GitLab project ID/path 等稳定引用。

## 2. 对象关系

```text
namespace + env + app
        ↓
服务记录（显示名、负责人、系统说明）
        ↓ 1:N
代码组件（GitLab project ID、组件角色、源分支、MR 目标分支）
        ↓ 1:N
部署历史（时间、commit SHA、镜像、部署链接）
```

采用 `namespace + env + app` 区分服务实例。同名 app 可出现在不同平台；一个服务可关联多个仓库（服务端、前端、配置/共享组件），一个仓库也可承载多个服务。

## 3. 环境与分支规则

全局默认值：`dev → develop`、`test → test`、`prod → release`。日志环境名为 `release` 时默认也映射到 `release` 分支。服务/仓库可显式覆盖 `source_branch` 和 `mr_target_branch`；项目当前 default branch 仅作为 GitLab 元数据记录，不自动替代环境映射。

读取故障时源码时优先使用 deployment 记录的 commit SHA，而非分支当前头。没有部署历史时，只能对照配置分支做标注为“不确定版本”的只读分析；不得据此自动创建修复分支或 MR。

## 4. 配置数据模型草案

`ui.namespaces[].envs[].apps` 为环境对应的服务列表，服务项包含 `name` 和 `repo`（`group/project:branch`）。该配置服务 UI 选择器；独立的 `service_catalog` 仍可扩展项目 ID、组件角色等映射信息：

```yaml
service_catalog:
  branch_defaults:
    dev: develop
    test: test
    prod: release
    release: release
  services:
    - namespace: default
      app: boeet-gateway
      display_name: 综合能源网关
      owner: platform-team
      repositories:
        - project_id: 29
          project_path: boeet-framework/boeet-gateway
          role: backend
          mapping_status: confirmed
          source_branch_by_env:
            dev: develop
            test: test
            prod: release
          mr_target_branch_by_env:
            dev: develop
            test: test
            prod: release
          deployments:
            - env: prod
              deployed_at: '2026-11-06T08:00:00Z'
              commit_sha: '<40-character SHA>'
              image: '<image:tag>'
              deployment_url: '<pipeline/deployment link>'
```

这只是 schema 草案。PAT、MCP Key 等凭据禁止出现在 `service_catalog`。当前 GitLab MCP 搜索得到的候选清单见 [待核对映射](service-map-candidates.yaml)；它们是导入素材，`proposed` / `unresolved` 记录未确认前不得作为生产事实。

### 静态与动态数据分开

- **服务绑定与分支规则**：先由受评审的 log-search `config.yaml` 配置，随服务注册/部署更新。
- **部署历史**：每条部署记录归属于具体 GitLab project，优先由 CI/CD 发布事件写入；MVP 可人工维护，但必须追加记录，不覆盖历史。一个服务有多个仓库时，各仓库 commit 独立记录，不能用一个 SHA 代表整个服务。
- 后续可迁移到 log-search 自身的数据库/管理 API；Skill 和 MCP 契约保持不变。

## 5. MCP 契约

当前 MCP 提供 `get_query_options` 和 `query_logs`，尚未提供代码仓库映射工具。建议新增只读工具：

### `get_service_mappings`

- 输入：可选 `namespace`、`env`、`app`；全部省略表示返回可见目录（需分页/限制）。
- 输出：匹配的 namespace/env/app、display name、repository 列表、GitLab project ID/path、组件角色、source branch、MR target branch、映射状态和有效部署摘要。
- 不返回 PAT、MCP Key 或任何仓库密钥。
- 区分 `confirmed`、`proposed`、`unresolved`；候选或歧义时返回原因，不静默选一个。
- 日志查询与映射查询权限沿用 MCP 认证；若将来需要按 namespace 授权，必须在服务端对两种工具采用相同的可见范围。

在该工具上线前，Agent 只能用 `get_query_options` 拿到的平台/环境/app 选择做日志查询；不能从 GitLab 同名项目推断唯一业务映射。

## 6. 接入与维护流程

1. 新增日志 app 时，同时在 log-search UI 配置和 `service_catalog` 登记 namespace/env/app。
2. 通过 GitLab MCP 选择并记录 project ID；必要时关联多个代码组件，明确 backend/frontend/config 角色。
3. 设置每个环境的源码分支和 MR 目标分支。默认采用 develop/test/release，覆盖必须显式写入。
4. 验证仓库与分支可访问；服务责任人确认映射后将状态设为 `confirmed`。
5. 部署流水线登记运行 commit SHA、镜像和时间；回滚作为新部署事件追加。
6. 新配置生效后，Skill 通过 `get_service_mappings` 读取；无需更改 Skill 文件。

## 7. Skill 消费方式

Skill 的前置依赖是 log-search MCP 与 GitLab MCP。排查时先查日志得到 namespace/env/app，再向 log-search MCP 请求该键的映射；随后调用 GitLab MCP 读取对应 commit。遇到缺失/歧义映射，Skill 停在只读报告并指出需要补录的字段，不自动猜仓库。

Skill 可以维持极少量稳定逻辑（工具调用步骤、证据要求、写操作边界），不能复制整份服务目录或把某个服务名写进指令。

## 8. 实施顺序

1. 将 [候选映射](service-map-candidates.yaml) 中的名称匹配项由服务负责人逐项确认；先处理跨平台重复 app、前后端同名和 unresolved 项。
2. 在 config 结构与校验中加入 `service_catalog`，保持旧版 UI app 字符串列表兼容。
3. 增加 `get_service_mappings` MCP 工具与接口文档，并为未匹配、冲突、无权限提供可区分结果。
4. 通过部署流水线登记 commit SHA 历史；在此之前避免宣称已准确定位故障版本。
5. 更新 Skill 使用映射工具，端到端验证新增服务只改 log-search 配置就可被新会话发现。
