# 日志应用与代码仓库映射

## 当前实现

服务与仓库分支的对应关系由 `log-search` 配置维护。每个 namespace 下按环境配置应用，应用项使用 `name` 标识日志中的应用，使用 `repo` 指向对应 Git 仓库和分支：

```yaml
ui:
  namespaces:
    - label: 默认平台
      value: default
      envs:
        - label: 开发
          value: dev
          apps:
            - name: boeet-gateway
              repo: group/boeet-gateway:develop
```

`repo` 格式为 `group/project:branch`。该映射绑定在具体的 namespace 和环境下，因此同一个 app 在不同平台或环境可以指向不同的项目或分支。缺少 `repo` 或值为空时，表示当前没有登记代码映射。

## MCP 查询方式

log-search MCP 的 `get_query_options` 会返回 namespace、环境及其应用选项；环境下的 app 项包含 `name` 和 `repo`。排查流程应先用日志查询确定 namespace、env、app，再从 `get_query_options` 返回值中找到对应应用并读取 `repo`。随后由 GitLab MCP 按该项目和分支读取源码。

新增或调整日志应用的仓库映射，只需更新 log-search 的应用配置并按其部署流程生效。调用方（包括 Skill）不应维护另一份服务目录，也不应仅凭相似的 app/project 名称推断仓库。映射缺失时应明确报告并请求补录或确认。

环境分支由每个 app 的 `repo` 显式给出。常见约定是开发使用 `develop`、测试使用 `test`、生产使用 `release`，但调用方应以 MCP 实际返回的映射为准，不应在 Skill 中另设默认值覆盖配置。

## 当前边界与后续扩展

当前映射表达一个 app 在一个环境下的单个 Git 仓库和分支，能够支持从日志定位到对应源码。它尚未表达多仓库组件关系、部署时的 commit SHA、历史部署记录、服务负责人或映射审核状态。

若后续需要精确还原故障发生时运行的源码版本，可另行扩展部署记录（例如环境、GitLab 项目、部署时间、commit SHA 和镜像版本）。这属于版本追溯能力，不影响当前通过 `get_query_options` 获取仓库及分支的方式。PAT、MCP Key 等凭据不得放入应用映射配置。

GitLab 项目匹配的候选整理见[候选映射清单](service-map-candidates.yaml)。该文件是待核对的导入参考，不是运行时映射事实；实际生效值以 log-search 配置和 MCP 返回为准。
